# Development Guide

> The single authority for this project's development conventions. Rotating AI
> reviewers and future contributors start here instead of reverse-engineering
> habits from commit history / changelogs. General Rust conventions (toolchain,
> dependency discipline, error handling, test layout) live in the
> rust-conventions skill; batch/text-processing boundaries live in the
> batch-ops skill.

## 0. Project Nature and Collaboration Mode

- **Rotating-AI development**: most code is written by AI and reviewed by AI,
  with the author intervening rarely and switching AI models. Therefore
  **code-as-documentation is the highest principle** — implicit knowledge must
  be made explicit, and structural contracts should be handed to the compiler
  rather than prose (see §4, the typestate pipeline).
- **Language**: communicate with the author in Chinese; code comments, doc
  comments and commit messages in English.
- **Real-user validation**: alga2 is a real user (~900 impls generated by this
  library); the design is validated against it.

## 1. Commit Convention

Lightweight Conventional Commits:

```
<type>: <subject>            # English imperative, ≤50 chars
```

- Allowed types: `feat` / `fix` / `refactor` / `perf` / `test` / `docs` / `chore` / `build`
- No scope for a single-crate project.
- Example: `feat: typestate preprocessing pipeline (Stream states enforce pass order)`
- Release commit: `chore: release 0.9.7 (version + docs sync)` with a summary
  in the body.

## 2. Quality Gate (run for every change; all green before committing)

```bash
cargo fmt --check                      # run cargo fmt first (lesson: skipping it reddened the CI fmt job)
cargo check --all-targets
cargo clippy --all-targets -- -D warnings   # zero clippy warnings
cargo test                             # lib + dsl + UI snapshots + doctests
cargo test --doc
cargo doc --no-deps                    # zero warnings
```

Snapshot updates: `BLESS=1 cargo test --lib golden` rewrites the golden
expansion snapshots (only for intentional render changes).

## 3. Release Flow (GitHub + CI green first, then crates.io)

1. **Unreleased placeholder**: during development, maintain `## Unreleased`
   at the top of the four changelogs (`CHANGELOG.md`, `docs/zh-CN/CHANGELOG.md`,
   `docs/dev-changelog.md`, `docs/zh-CN/dev-changelog.md`). Record each change
   as it lands — never batch-write them at release time.
2. **At release**:
   - Bump the version in `Cargo.toml`;
   - Update the head version line (`README.md`, `docs/tutorial.md`,
     `docs/architecture.md` and their zh-CN counterparts — EN replaces with
     `**vX.Y.Z** (date) — summary`; the zh-CN architecture **appends** a line
     per version, it does not replace);
   - Sync the README dependency example (`batch-impl = "X.Y.Z"`);
   - Turn the four `## Unreleased` sections into `## X.Y.Z (date)`, keeping
     the summary line;
   - `cargo package --list` and eyeball the manifest (no unrelated files —
     lesson: `rust-2024-feature.md` once shipped inside every `.crate`);
   - commit `chore: release X.Y.Z (...)` → `git tag vX.Y.Z` →
     `git push origin main --tags`;
   - **only after CI is fully green** (fmt / clippy / test-stable /
     test-MSRV / test-Windows / doc) run `cargo publish`; if a fix commit
     lands after the tag, move the tag with `-f` and force-push it.
3. **After release**: create the GitHub Release
   (`gh release create vX.Y.Z --notes "..."`).

## 4. Architecture Contracts (read before changing code)

- **Typestate pipeline** (`src/preprocess/stream.rs`): the preprocessing
  order is enforced by the type system, not by comments. New passes must be
  added inside the `Stream<S>` state chain — either as a new transition on an
  intermediate state before `Paired`, or on one of the tail branches
  (`expand_tokens` / `reject_directives` / `where_process`). The free
  functions stay `pub(crate)` for fuzz to call directly (fuzz deliberately
  bypasses the chain); do not remove the `expand_consts` canary
  `debug_assert!`. Name states after **invariants**, not passes; only a
  transition that establishes a new invariant deserves a state.
- **Single-authority philosophy**: cross-module predicates are collected in
  one place — `util/punct_ops.rs::read_op` (operator shapes),
  `util/diagnostic.rs::compile_error_str` (error construction),
  `util/scan.rs::is_impl_template` (`impl{...}` discrimination),
  `entry/impl_spec.rs::chunks_to_streams` (where-chunk splitting),
  `ast/fresh.rs::is_carrier_at` (carrier recognition). On finding a
  duplicate predicate, consolidate — never fork another copy.
- **Syntax freeze (since 0.7.2)**: the semantics of every existing token are
  final; new releases only **add** (directives / constants / tools), refine
  diagnostics, and polish docs. Any semantic change is a deliberate breaking
  release.
- **Diagnostic spans**: point at the user-visible token (the `err_ty_at`
  level), never a bare `Span::call_site` (the impl-entry / shape diagnostics
  are already consolidated; use `syn::Error::span()` / leaf-token spans where
  available).

## 5. Documentation Discipline (bilingual, five files, doctests)

- **Bilingual sync**: EN is the release artifact; zh-CN is written first during
  development. Five files × two languages: `README`, `tutorial`, `architecture`,
  `dev-changelog`, `CHANGELOG`. A change to one language must be mirrored in
  the other before release.
- **Tutorial code blocks are doctests**: the ```rust blocks in
  `docs/tutorial.md` and `README.md` are compiled by lib.rs's
  `#![doc = include_str!]` — they must compile after any edit.
- **docs.rs first screen**: README is part of the lib.rs docs; any front-page
  restructure must keep "Why use it" + the minimal example on top and the
  version banner to one line linking the CHANGELOG.
- **Documented examples must be true**: readers/reviewers verify them
  item by item (the splat-27 example and the `Box.Box u8` associativity were
  both caught wrong by testing). Verify any expansion you write into docs.

## 6. Dependencies and Toolchain

- **Never add a crate unprompted**: explain the use and get consent first
  (exception: the user explicitly asks).
- Toolchain: latest stable, edition 2024, MSRV 1.95 (**deliberate**:
  `Cell::update` + match-arm if-let guards stabilized around 1.87/1.88; 1.95
  leaves a stable margin — changing the MSRV requires a real build probe and
  updating the CI `test-msrv` job).
- Error handling: thiserror preferred, hand-written enums for simple cases;
  no unsolicited anyhow.
- Async: tokio by default; never introduce an async runtime unprompted.

## 7. Syntax Style Preferences (author-specific, do not override)

The author has explicit, deliberately-consolidated syntax preferences;
review against them:

- **Chaining over wrapping**: prefer `val.into()` and combinator chains over
  explicit wrappers like `Some(val)` / `Box::new(val)` — unless the explicit
  type carries information.
- **Inference over annotation**: `let x = 1` over `let x = 1u32` /
  `let x: u32 = 1`; put type annotations at the call site (turbofish) —
  `(1..100).collect::<u32>()` over `let x: u32 = (1..100).collect()`;
  use the well-known short forms (`vec![]` over `Vec::new()`; use
  `format!` / `Default::default()` when they fit).
- **Concision over complexity**: make it as short as it can be — no
  needless intermediate variables or repeated structure; never at the
  cost of readability.
- Full details: the rust-conventions skill, "three style principles".

## 8. Test Layout

- Default: inline `#[cfg(test)]` modules; move to `tests/features/` when a
  suite grows large or cohesive (per-feature modules under 350 lines, mounted
  by `tests/dsl.rs`).
- UI snapshots (trybuild) live in `tests/ui/`; golden expansion snapshots in
  `tests/golden/`.
- Fuzz (`src/testing/fuzz.rs`) calls passes directly and tolerates
  out-of-order input — it is the second line of defense outside the typestate
  chain, paired with the canary assertions; keep both when touching passes.

## 9. Packaging Hygiene

- Before release, run `cargo package --list` and eyeball the manifest:
  unrelated files (local notes, probes) must not ship.
- Do not commit probe files (`tests/_iso/` is a scratch zone; lesson: it was
  committed twice by accident).

## 10. Boundaries (what not to do)

- Do not use PowerShell for text replacement / writing / batch processing
  (see batch-ops: literals via edit/write, regex/batch via rust tools).
- Do not leave process discipline only in comments — if it can be collected
  into a type/assertion, collect it; if it can be collected into prose,
  collect it here.
